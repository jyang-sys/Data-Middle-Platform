# 第二阶段：销量试算报表

本阶段参考内部手工报表的月份、平台、产品类型、型号、配置和每日数量布局，直接使用中台独立保存的 `base_orders`、`base_order_items` 及订单归属生成报表。全部页面与导出注明“试算”，暂不认定为最终净销量或正式人员业绩。销售额、利润、库存联动和补货计算不在本次范围。

## 模板对应功能

| 手工报表结构 | 中台实现 |
| --- | --- |
| 按平台汇总、按型号汇总 | 年月 × 型号/规格 × 平台销量矩阵，以及两个 Excel 长表 |
| 月度型号与平台销量 | 查询完整月份，包括月末 31 日；型号合计或配置、颜色明细；按销量排序 |
| 各平台每日统计 | 产品类型、型号/规格、平台 × 所选范围的每一天 |
| 所有平台当月销售汇总 | 每日平台件数、每日合计、期间合计，以及每日走势 |
| 明细核对 | 每个汇总行展开同年月、同商品的订单明细；全量明细分页与 Excel 导出 |
| 手工表中的平台/小组合并名称 | 平台、小组、人员、店铺独立筛选和汇总，小组采用订单已保存归属 |

内部文件包含重复汇总与不一致的历史数量，还包含人为合并多个配置的名称。因此只参考布局，不将汇总行或重复工作表导入订单库，也不把月度记录伪造为每日订单。文件与内部数量不提交仓库。

## 统计口径

- 数量为商品件数，一笔订单两件计 2；订单数量另按 Base 订单 ID 去重。合法数量必须为非负整数；异常明细不计入并提示数量。零件明细保留用于核对。
- 最近 3、7、14 天包含当天，按所选 IANA 时区的自然日统计。支持月份、自定义范围（最多 366 天），月份分组包含年份。没有销量的日期仍显示 0。
- 默认以 Base 创建时间 `date_add` **试算**，不是订单确认时间、发货时间或月底导入时间。来源字段与平台原始下单时间的关系尚待核对。
- 可切换到本地附加字段 `platform_order_date`；支持 ISO 日期、时间戳（有时区则转换，无时区则使用报告时区）。日期缺失或格式无效时不替代为其他时间，并显示缺失数量；该诊断涵盖符合其他订单筛选的订单，无法判断其所属日期范围。
- 默认仅已确认订单，可取消这一限制；状态 ID 为可选计入列表。取消、退款、部分退款、退货的最终扣减规则留待业务确认，不依据未知状态 ID 自动判断。
- Base `order_return` 来源单据与本地附加字段 `exclude_from_sales: true` 排除，页面展示排除数量；此规则用于隔离退货来源/人工标记单据，不代表已经实现全部退货净扣减。虚拟记账、借货重复单据如无可靠来源标识，须维护排除标记。不同 Base 订单 ID 的同一真实交易目前不会自动识别为重复。
- 人员、小组采用订单保存的 ID 和名称快照；未分配单独显示，并计入总量。不会以库存所属小组、借货来源或当前店铺默认归属代替历史销售归属。兼容旧文本归属，但不按同名猜测员工 ID。
- 月度、每日、平台商品、小组、人员、店铺各视图由同一次读事务获取的同一明细集合计算；明细、导出使用相同筛选函数。后续同步或人工修改发生在不同请求之间时，结果会变化，本阶段没有冻结报表快照。

本地附加字段可在“员工与归属 → 订单归属 → 单笔维护”中保存，例如：

```json
{
  "platform_order_date": "2026-07-31T18:00:00+08:00",
  "exclude_from_sales": false,
  "活动": "业务维护的活动计划"
}
```

附加字段对象保存时整体替换，应先读取并保留其他已有字段。Base 重复同步不覆盖本地附加字段和归属。

## 型号与规格归并

`父 SKU`、`子 SKU` 是来源产品关系，不自动等同业务型号、配置和颜色。新增独立 `sales_sku_mappings`，将 `(平台, 原 SKU)` 显式对应 `(型号, 配置, 颜色, 产品类型)`。映射不修改源产品或订单 JSON。

- 平台专用映射优先；`*` 表示明确确认同一原 SKU 在各平台通用。不同编码可以映射到同一型号、配置、颜色。
- 型号合计汇总所有配置、颜色；规格明细按三个字段组合区分，显示名称相同也不合并不同组合。
- 未映射编码保留平台与原 SKU 单独显示，不猜测配置顺序或拆分模板中的多配置名称。页面提供未映射清单和映射维护入口。
- 映射保存带版本保护，过期版本返回 409；实际变更记录前后值、操作人和原因。当前映射重新计算历史查询，无结账冻结；修改映射后需重新查询。

## 接口与导出

- `GET /api/reports/sales`：试算汇总、每日走势数据、归属汇总、诊断和口径。
- `GET /api/reports/details`：同口径商品明细，默认 50、最多 200 行分页；`month`、`key_json` 用于精确展开。
- `GET /api/reports/export`：7 个工作表，包括两个长表、月度平台矩阵、平台商品每日统计、全平台每日销量、订单明细、口径说明。文本保持 Excel 文本类型，避免商品编码被解释为公式。
- `GET /api/reports/options`：平台、店铺、状态和已维护商品选项。
- `GET /api/reports/mappings`、`PUT /api/reports/mappings`、`GET /api/reports/mappings/history`：映射查询、维护、审计。

汇总、明细和导出共享参数 `start/end/timezone/date_basis/confirmed_only/status_ids/platform/shop_id/group_id/employee_id/model/source_sku/product_type/granularity`。状态列表用重复 `status_ids` 参数。店铺 ID 必须同时指定平台。页面编辑筛选后，表格与导出仍使用最后一次成功查询的筛选，并提示重新查询。

报表当前在进程中读取订单和商品明细后计算，适用于开发验证阶段；扩大历史订单规模后需要 SQL 聚合、索引和任务化导出。当前单用户环境不包含登录权限或正式结账。

## 验收标准与验证

1. 同一筛选下月度、每日、平台商品、小组、人员、店铺及全量明细的件数合计相等；多件订单与订单笔数区分。
2. 同规格跨平台合并，型号合计包含全部配置与颜色；未知编码和显示名称碰撞不造成误合并。
3. 整月包含 31 日，跨年同月不混合，零销量日期补齐；时区边界与人工维护的平台日期正确，缺失日期不替代。
4. 手工排除、来源退货排除、确认状态和状态 ID 筛选生效，试算标识与诊断可见。
5. 历史销售归属保留，库存借货组不影响销售组，重复同步保留本地维护值。
6. 汇总行可核对订单明细并分页；Excel 各数量与页面一致，文本不转为公式。
7. 映射更新有版本冲突保护和变更历史；源订单、产品记录不被改写。
8. 服务页面、静态路由、内嵌资源预览均有样式；手机屏幕的宽表在表内滚动。

自动测试采用临时数据库与合成订单；浏览器验收采用独立示例数据库，覆盖查询、明细、映射保存、历史、Excel 下载和手机布局。正式上线前仍需确认原始平台日期、SKU 清单、取消/退款/退货扣减以及权限规则。
