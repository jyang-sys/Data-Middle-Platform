# 产品、销售归属与库存份额：第一版实现

## 数据分工

Base 同步 `base_*` 来源表；公司层级与编码映射、销售规则和明细归属、库存份额、登录账号分别独立建表。只读访问 Base，不向上游新增对象或写回库存。本地演示与真实数据库分开。

## 公司产品

`company_products` 支持任意父子层级：`group` 作为汇总节点，`sku` 为具体规格。SKU 不能有下级；循环、编号重复、父节点停用和有下级/关联时的类型变更均校验。颜色与配置作为属性独立保存，不从名称猜测。

`product_source_links` 将来源关联到具体规格：

| 范围 | 唯一键 |
| --- | --- |
| 来源产品 | 目录 ID＋产品 ID |
| 销售编码 | 平台＋店铺（可留空）＋原 SKU |
| 仓库来源产品 | 目录 ID＋仓库标识＋来源产品 ID |

销售优先匹配店铺专用编码、平台通用编码、明确的 Base 产品关系；库存优先匹配仓库专用关系，再使用目录产品关系。映射不是推测的“海外仓 SKU”字段，实际来源标识保留。父体按全部下级明细逐层汇总，不新增父体事实数量。修改产品树/映射会重算历史分类，保留版本和审计，尚无结账冻结。

## 销售归属

所有报表、明细及 Excel 从同一订单商品选择派生，支持平台→店铺、产品→平台→店铺、小组→人员，以及公司产品树。订单数独立去重，同一订单跨团队时团队订单数不直接相加。

归属优先级为：人工明细修正→人工订单归属/明确锁定→已保存规则快照→可选规则试算→未分配。规则按 SKU/公司产品节点或店铺配置，带生效区间；同范围区间重叠禁止。先比较商品规则、店铺范围、平台范围、目录范围，再比较产品节点深度；精确原 SKU 在相同范围下优先于产品节点。公司父体规则覆盖后代，更深节点优先。

来源同步在同一事务中为首次出现的新订单保存规则匹配快照（人员、小组名称及 ID、规则 ID/版本）。当前自动匹配日期暂用 Base 创建时间、`SALES_ASSIGNMENT_TIMEZONE`（默认上海），不认定为已核实的平台原始日期。后续确认平台日期后需调整这一步；不能用它宣称正式业绩结算。

已有订单不因新规则或重复同步自动补分配；历史补分配先预览当前销量范围，再携带预览 token 保存，每次最多 500 条。明细/规则变化使 token 失效。已保存归属可逐商品人工修正，带归属版本和来源指纹；来源商品身份变化后旧快照不沿用。来源数量变化保留原归属。源订单 JSON 从不改写。

规则读取/停用、归属修正由管理员维护；已登录操作的审计操作人从服务端会话取得。规则保存了名称快照，人员调组后要配置新的生效规则，不能假定旧规则自动跟随。

取消/退款/退货仍为可配置试算，默认确认条件和排除项沿用销量报告。正式原平台日期、退货净额、结账冻结不在本次确认范围。

## 库存归属

`stock_allocations` 对一条“目录＋来源产品＋仓库”选择唯一归属方式：

- 未分配：来源库存不自动归某组。
- 编码归组：整条来源记录属于一个小组，份额随来源数量变化。
- 数量拆分：按组维护绝对件数，如 30/30/40，来源变化不自动改份额。

每组份额可包含多个独占平台/店铺分配及共享池；剩余为组内未分配。独占渠道总量与共享池总量共同受小组份额约束。共享池在全量视图单独展示；按某平台筛选只计该平台的独占数量，不将共享池复制到各平台。

保存使用份额版本和来源 token，同时校验来源数量、更新时间，拒绝超分配。来源为未知、负数或非整数时不能新增件数分配。来源后续减少时保留旧份额，显示负差额；渠道超出新份额同样标记冲突。修改只调整业务账本，不直接扣来源库存、不推送平台可售库存。

库存类型人工确认并审计：待确认、实物、虚拟、退货待检、报废、运输在途。虚拟/退货待检/报废/运输在途不能新增渠道分配。只有明确标为实物的来源数量进入实物合计；未确认明细另列，不能将部分已确认值误认成全部库存。来源 `incoming`/`reservations` 保留，不自动换算实物可用量。

库存汇总按公司规格合并历史来源编码，仓库展开保留来源明细；各组只看其份额。跨目录实物合并依赖管理员确认每条记录的物理含义，重复的虚拟镜像必须正确分类，系统不凭仓库名称猜测。来源原有矩阵、分页核对视图保留在折叠区。

本次为管理员直接维护、版本保护与变更历史；负责人审批、借货申请/归还工作流、跨系统预占及分配回写仍待后续实现。

## 账号和数据范围

首次点击“启用账号权限”建立管理员后，API 要求登录。密码 PBKDF2 哈希保存，cookie HttpOnly/SameSite Strict，登录限速，会话最长 24 小时，账号修改后撤销会话。HTTPS 请求下 cookie 标为 Secure；正式部署需 HTTPS、正确代理配置和安全运维。`APP_REQUIRE_LOGIN=1` 可在未建首个管理员时也阻止业务 API，部署前先在回环环境完成管理员配置。

| 角色 | 销售范围 | 库存范围 | 写入 |
| --- | --- | --- | --- |
| 管理员 | 全部，含未分配 | 全部 | 管理数据与账号 |
| 老板 | 全部，含未分配 | 全部 | 只读 |
| 小组负责人 | 保存归属中的本组 | 本组份额 | 当前只读 |
| 运营人员 | 保存归属中的本人 | 本组获授权的份额 | 当前只读 |

权限在后端过滤后才聚合，明细和 Excel 同范围；其他角色不能访问原始订单、旧版分析、表格 SQL 或管理写接口。原来源库存接口为受限账号返回本组份额，不返回完整实物和其他组份额。首个账号建立前仅供回环地址本地开发，不视为可公开部署。跨组借货可见权限、审批角色和按 SKU 进一步细分库存授权后续补充。

当前按目录全量读取、进程内汇总，适用于开发演示；大规模数据需 SQL 聚合、分页和任务化导出。登录权限第一版不等于完整生产部署。

## 验证

`scripts/check.sh` 执行临时数据库测试与前端语法检查。新增测试覆盖层级循环、来源映射、跨平台汇总、明细规则快照、历史预览冲突、来源身份变更、人工明细修正、库存两种归属、30/30/40、来源减少差额、共享池不重复、服务端角色及导出越权、登录限速和最后管理员保护。

`scripts/seed-business-demo.py` 生成隔离的本地合成演示数据及核对文件，拒绝覆盖数据库，不调用 Base。Base 测试账号搭建提示词见 [base-demo-prompt.md](base-demo-prompt.md)。

本次验证：66 项自动测试通过；浏览器验证销量核对、父体明细展开、200 台合计、单组 60 台、Amazon 独占 20 台、超分配拒绝、CSV、产品创建、明细修正入口、移动端，以及管理员设置与老板/组长/个人隔离。私有静态演示快照验证产品树及库存 200/60/20 筛选。未向 Base 写入或创建任何演示对象。

启用登录的服务不提供匿名快照构建入口；当前 build-preview 脚本用于回环环境的独立开发库，不能绕过已启用的账号权限。
